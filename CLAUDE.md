## The project

We are building a system that decides whether a speech recording is **real**
(a human, called *bona fide*) or **fake** (generated by AI text-to-speech or
voice conversion, called *spoof*).

B.Tech major project, team ID MP2026CSE309, Graphic Era Deemed to be
University, supervised by Dr. Vidit Kumar. Four team members. Two semesters.

The point of the project is **not** a clever new model. It is a careful
comparison: we fix one simple baseline, then run six experiments that each
change exactly one thing, so we can say precisely which technique helped and
by how much. Reproducibility is the deliverable.

## Teaching mode — important

The team is learning this domain while building it. We need to understand the
code, not just possess it. So:

- **Explain before you write.** Describe the approach in plain language, then
  wait for us to say go.
- **One file per turn.** Do not generate five files at once, even if you can.
- **Explain after you write.** Walk through what each function does and why
  it's shaped that way.
- **Name the alternatives.** If you chose librosa over torchaudio, or 25 ms
  windows over 20 ms, say what the other option was and why this one won. If
  the honest answer is "convention, it doesn't matter much", say that.
- **Answer "why" properly.** Never wave a question away as obvious.
- **Flag it when we're about to do something wrong**, especially anything that
  would break reproducibility or make our numbers non-comparable with
  published ASVspoof results.

Keep the code simple and readable over clever and short. A beginner on this
team should be able to read any file and follow it.

## Stack

Python 3.9+ only. No C++, no MATLAB, no Java.

PyTorch + torchaudio, librosa + soundfile, numpy, scipy, pandas,
scikit-learn, matplotlib, PyYAML, pytest. Streamlit in phase 8.

Note: the official ASVspoof LFCC and CQCC implementations are MATLAB. We are
writing Python versions. When you do, say so in a comment — do not imply they
are the originals.

## Five rules that don't bend

1. **Settings live in `config.yaml`, never in code.** Sample rate, window
   size, number of mel bands, input length, learning rate, seed. If you're
   typing a number into a `.py` file and it changes what the model learns,
   stop and put it in the config.
2. **Never commit data.** No audio, no feature caches, no checkpoints. `data/`
   is gitignored. If you see one staged, say so loudly.
3. **Use the official train/dev/eval split exactly as distributed.** No
   reshuffling, no custom splits, no balancing the classes. The imbalance is
   real and experiment E5 is about handling it. Dev is for tuning; eval is
   scored once, at the end.
4. **Never report accuracy.** The data is roughly 1:9 real to fake, so a model
   that says "fake" every time scores 90%. Use Equal Error Rate (EER) and
   min t-DCF.
5. **Never invent results.** If a script hasn't been run, say it hasn't been
   run. Do not fill a table with plausible numbers.

## The six experiments (phases 4–6)

| No. | What changes | Question |
|---|---|---|
| E1 | Front-end: log-mel vs LFCC vs CQCC | Which representation shows fake artefacts best? |
| E2 | Augmentation: SpecAugment, noise, codecs | Does it help on unseen conditions? |
| E3 | Model size: shallow vs deeper CNN vs MFM | Does more capacity help or overfit? |
| E4 | Input length: 2 s vs 4 s vs full | How much audio is needed? |
| E5 | Loss: BCE vs weighted BCE vs focal | How to handle the class imbalance? |
| E6 | Fusing the two best systems | Do they make different mistakes? |

Everything in phases 1–3 exists to make these six comparisons cheap and fair.

## Out of scope — do not build

Replay attack detection, identifying which AI generated a sample, finding an
edited region inside a longer recording, partially fake utterances, speaker
identification, real-time streaming detection.
